# MacOBlox

Клиент Roblox для macOS (x86_64) на Linux через Darling. Состояние на
2026-09-23: главное меню, вход (Quick Login), аватар и игры работают.

## Запуск

Лаунчер: `launcher/install.sh` ставит пункт «Mac O Blox» в меню приложений
и команду `macoblox`. Там запуск игры, фастфлаги, DNS только для Roblox,
чувствительность камеры, обновление клиента, диагностика. Настройки лежат в
`~/.config/macoblox/settings.json`, логи в `logs/`.

Приоритеты: игра в Darling идёт с nice −4, а darlingserver, демоны Darling и
pw-cat наследуют nice лаунчера (+10, если его так запускает рабочий стол) и
голодают, пока игра занимает все ядра. Лаунчер поднимает darlingserver с
демонами до −5 и pw-cat до −11, насколько позволяет RLIMIT_NICE.

## Что делает шим (build/libMacOBloxShims.dylib)

Собирается `build_debug_shim.sh` из:

- `libMacOBloxShims.m` — AppKit/GL/ввод: возврат GL-контекста после
  CALayerContext, номера кнопок мыши как в macOS, захват мыши для камеры,
  курсоры, недостающие методы NSEvent/NSTextView/NSButton/CNContactStore,
  cookie с сохранением на диск (`~/Library/MacOBlox/Cookies.plist` внутри
  префикса Darling), скрытие полоски меню, иконка окна.
- `missing_symbols.c` — функции, которые Roblox импортирует, а Darling нет.
- `net_trace.c` — надёжный приём UDP и сторож зависших потоков RakNet.
- `darling_fixes.c` — мьютексы без потерянных пробуждений Darling; usleep и
  nanosleep идут прямо в Linux (в Darling каждый — два запроса к darlingserver).
- `memory_stats.c` — память системы и самой игры (phys_footprint для «Mem»).
- `thread_kick.c` — «пинок» (SIGURG) потокам, застрявшим в ожидании Darling:
  сторож UDP и долгие ожидания мьютекса; место застревания пишется в лог.
- `xfixes_raw.c` — скрытие курсора через XFixes по своему X11-сокету.
- `dns_override.c` — DNS для Roblox через локальный прокси лаунчера.
- `xattr_compat.c`, `exit_compat.c` — от прошлых этапов.

Переменные `MACOBLOX_*` (трассировки, DNS, чувствительность) задаёт
лаунчер. `run_debug.sh` остался для ручной отладки.

## Важно про Darling

Не удалять и не менять файлы в `~/.darling` с хоста, пока работает
darlingserver: оверлей Darling перестаёт показывать хосту новые файлы.
Удалять изнутри (`darling shell rm ...`) или при остановленном сервере.

## История

## Диагностический запуск

Из обычного терминала Linux:

```bash
cd MacOBlox
./run_debug.sh
```

Скрипт собирает библиотеку из `libMacOBloxShims.m` в `build/`, запускает
клиент из папки проекта в существующем префиксе Darling и записывает
вывод в отдельный файл `logs/launch-*.log`. Аргументы передаются клиенту.
Сам запуск требует работающего Darling вне ограниченной среды Codex.
Скрипт запуска пока не проверен в работающем Darling.

Только сборка: `./build_debug_shim.sh`. Можно задать `DARLING_SYSROOT`.
Старые библиотеки в корне и внутри `.app` сохранены; новая выбирается
через `DYLD_INSERT_LIBRARIES` и `DYLD_LIBRARY_PATH`.

## Изменения 2026-09-26

Проверено набором тестов под Darling (сеть, мьютексы, ожидания, звук,
куки); старая сборка валит новые тесты, новая проходит все.

- Ожидания с тайм-аутом в Darling возвращают 0 вместо ETIMEDOUT (100 мс
  ожидания — 0 через 100 мс). Поэтому нарезка ожиданий в `darling_fixes.c`
  никогда не росла (каждый отрезок 50 мс — запрос к darlingserver), а
  вызывающий не видел тайм-аута. Теперь истёкший срок определяется по часам;
  для `pthread_cond_timedwait_relative_np` (Roblox его импортирует) время
  уже отожданных отрезков вычитается, иначе ожидание дольше секунды не
  кончалось никогда.
- kqueue: Roblox закрывает сокеты через `close$NOCANCEL` без EV_DELETE, и
  запись о сокете оставалась: следующий сокет с тем же номером получал
  события старого владельца (крутится поток, возможен use-after-free в
  Asio). `close`/`close$NOCANCEL` перехвачены, записи сверяются по inode.
- Проверка «есть ли данные» теперь через `poll`, а не `recv(MSG_PEEK)`:
  любой приём, даже peek, забирает ошибку сокета (ICMP «port unreachable»),
  и после этого `recv(MSG_DONTWAIT)` на блокирующем сокете висел вечно.
- Пинки сторожа UDP — только для сетевых сокетов (AF_INET/AF_INET6), не для
  локальных пар, которыми потоки будят друг друга; ждущий мьютекс поток
  перед пинком проверяется повторно.
- Куки: `cookiesForURL:` Darling игнорирует URL, а `setCookies:forURL:…`
  ничего не делает. Хранилище теперь своё: домен, путь, Secure и срок
  проверяются (логин больше не уходит на чужие хосты и по http), новое
  значение заменяет старое, запись файла атомарная, сразу 0600; сессионные
  куки только в памяти; чужой домен в Set-Cookie отвергается.
- Очередь событий: «нет события» — тип 100, как у Darling (NSApplication
  сравнивает с 0x64). Тип 13 был настоящим событием в точке (0,0).
- Клавиши: при FocusOut таблица нажатых клавиш сбрасывается (Alt+Tab с
  зажатой W больше не оставляет её «нажатой» для CGEventSourceKeyState).
- Захват мыши: пока идёт наш warp, события движения не склеиваются; если
  движение от warp так и не пришло, центрирование возобновляется через 8
  событий (раньше отключалось до конца захвата).
- Поток XFixes спит на pipe, а не опрашивает каждые 5 мс через usleep
  Darling (400 запросов к darlingserver в секунду); запускается при старте.
- getaddrinfo: пауза между попытками без блокировки, повтор только при
  временных ошибках, ожидание прямыми снами Linux.
- Хуки исключений, makeCurrentContext, flushBuffer: getenv и dlsym один раз,
  а не на каждый throw или кадр (ошибки Lua в играх — C++-исключения).
- Шейдеры: исправление для Mesa применяется ко всем шейдерам (не только к
  первым 8192), исходники хранятся только с `MACOBLOX_TRACE_GL=1`.
- `fast_libc.c`: SSE-циклы вместо `rep movsb/stosb` там, где те медленнее
  (короткие копии, 4K-алиасинг, больше L2), быстрые memchr/strlen/strcmp,
  перехвачены memset_pattern4/8/16.
- Переключатели `MACOBLOX_*=0` теперь означают «выключено».

## Изменения 2026-09-26, вечер: блокировки без darlingserver

- В Darling мьютексы и условные переменные (psynch) ждут через
  darlingserver: каждый захват под нагрузкой, каждое ожидание и сигнал —
  запрос к серверу (40% ядра в игре), пробуждения теряются, а условные
  переменные ломаются (тайм-аут приходит как пробуждение, счётчики
  расходятся, дальше «psync_cvwait; invalid sequence numbers» и EINVAL на
  каждое ожидание — 12 874 раза за 7 минут в логе сервера).
- Теперь в `darling_fixes.c` занятый мьютекс ждёт на futex Linux (таблица
  по адресу мьютекса, будит `pthread_mutex_unlock`), а условные переменные
  свои: очередь ждущих, у каждого свой futex; сигнал будит ровно одного,
  broadcast — ровно ждущих, сигналы процесса ожидание не прерывают.
  Условные переменные, созданные самим Darling (подпись 'COND'/0x434F4E45,
  process-shared), остаются его. Тест «очередь»: 13,6 с и 18,5 с CPU
  darlingserver → 0,13 с и 0,04 с.
- `PTHREAD_MUTEX_USE_ULOCK=1` (режим libpthread на ulock) не подходит:
  его условные переменные зовут `__ulock_wait2` (syscall 544), которого в
  Darling нет — процесс падает на первом ожидании.
- Лаунчер: «Перезапустить Darling» останавливает весь контейнер (launchd и
  демоны — не дети darlingserver и оставались сиротами по ~250 МБ), при
  старте убирает процессы Darling без живого сервера и ждёт, пока
  закроется предыдущая игра (иначе обе делили один сервер и падали вместе).

## Что проверить дальше

Нужен свежий лог запуска из обычного терминала. По нему определить, где
останавливается клиент: загрузчик, загрузка NIB, создание окна или рендер.
По воспоминаниям владельца, ранее движок начинал работу, но изображения не было;
старый лог, подтверждающий это, пока не найден.

В старом коде остаются потенциальные проблемы: часть фатальных сигналов
подавляется, обработчик сбоев вручную разбирает контекст и стек. Эти места
требуют отдельной проверки. Строковые константы Cocoa исправлены на NSString.
`build_shims.py` — старый скрипт, который непосредственно меняет фреймворки
в `~/.darling`; новые скрипты его автоматически не запускают.
В `ffmpeg_compat/` стоят ссылки между разными версиями ABI; совместимость
не проверена, новый запуск не добавляет эту папку в пути библиотек.

Доступ к файлам хоста через `/Volumes/SystemRoot` описан в документации:
https://docs.darlinghq.org/internals/basics/containerization.html

## Проверка после перезагрузки, 2026-09-21 16:21–16:29

Ядро 7.2.6-1-cachyos; Darling запускается. В run_debug.sh добавлен
DYLD_FORCE_FLAT_NAMESPACE=1: без него dyld не находит константы из shim.
Это экспериментальный глобальный режим поиска символов, способный менять
выбор символов и в других библиотеках.

Исправлены строковые константы (NSString вместо char*) и смещение регистров
в диагностике x86_64 mcontext (блок exception state занимает 16 байт).
Ранее выводимый RIP был значением RFLAGS, а настоящий сбой оказался в
objc_msgSend при CFNotificationCenterAddObserver с C-строкой из shim.

Добавлены только отсутствующие методы:
- NSView convertSizeToBacking: — экспериментальное преобразование 1:1;
  не реализует Retina или произвольные трансформации.
- CALayer contentsScale / setContentsScale: — хранение свойства;
  масштабируемый рендер этим не реализован.
- NSView allowedTouchTypes / setAllowedTouchTypes: — хранение свойства;
  генерация touch-событий не реализована.

Подтверждено логом: MainMenu.nib загружен, RBXWindow создан,
RobloxPlayerAppDelegate назначен, NSApplication run вызван.
Отображение окна/картинки и работоспособность игрового движка НЕ подтверждены.

Следующий блокер: `Failed to initialize crash reporter`, std::runtime_error
из RobloxPlayer по адресу возврата 0x105606b21, вызов из 0x10002f4aa.
Первоначально этому предшествовали ошибки getxattr/setxattr. В xattr_compat.c
добавлен адаптер только для org.chromium.crashpad.* и com.googlecode.crashpad.*:
Linux namespace user., доступ через fd, ENODATA преобразуется в ENOATTR.
Другие имена и ненулевые position/options остаются у Darling.
Данные реально записываются в атрибуты; успех не подделывается.
После адаптера сообщения xattr исчезли, но инициализация reporter всё ещё
завершается ошибкой без уточнения причины. Причина следующего сбоя не установлена.

(`--crashCounter must be specified` при --help); без shim не загружается.

Логи: logs/touch-types.log (ошибки xattr), logs/xattr-compat.log (после исправления),
logs/crash-handler-with-shim.log. Время запуска и код выхода также записываются
в отдельные logs/launch-*.log.

Проверка xattr отдельной dylib и tests/xattr_compat_probe.c в Darling прошла:
